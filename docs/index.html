兩個名詞,先一句話講清楚

FHIR 是什麼?
醫療資料交換的國際標準格式(像醫療界的 JSON/表單規格)。健保的事前審查規定用它來交換申請。你不用懂它 —— 我們把你的資料翻成它。
CQL 是什麼?
健保把「哪種藥、什麼條件才給付」的審查規則寫成的公開格式。我們拿同一套官方規則,在你送出前先對這筆申請跑一遍。

我們在流程裡做什麼(五步)

① 產組申請 — 把你給的案子描述組成一份 FHIR 文件(Bundle),保證過官方驗證 0 錯誤。
② 驗基本檢查 — 藥 ↔ 適應症是不是合法組合。
③ 查CQL 送前自查 — 用健保官方規則跑一遍,三態: 通過 會被核刪 缺資料待補
④ 送提交 給收件端。
⑤ 回收核定回應(注意:受理 ≠ 核准,核定是事後才有)。

怎麼接進你既有的系統?

核心概念:你的系統已經有這筆申請的資料 → 填成一個中性的 PACase(完全不碰 FHIR)→ 呼叫我們一行。

情境 A ── 癌症藥物要打健保

// 你的腫瘤科系統已有這筆資料，填成中性描述（不需懂 FHIR）：
var c = new PACase(
    Ig: "...nhi.pas", CaseType: "cancer-drug",
    Patient:  new(){ ["id_card"]="…", ["birth_date"]="…" },
    Provider: new(){ ["hospital_code"]="…" },
    Vitals:   new(){ ["weight_kg"]=60 }, Created: "2026-09-30",
    Data:     new(){ ["drug_code"]="BC27730100", ["diagnosis_icd"]="C50.9", /* 檢測、影像… */ });

// 一行：組 FHIR + 種子檢查 + CQL 送前自查
var r = await Pipeline.RunAsync(c, cql: myCheck);

if (r.Blocked)  // 三態：會被核刪 / 缺資料待補 → 先修再送，別白白被扣錢
    ShowReasons(r.Cql);
else            // r.Bundle 就是可提交的 FHIR
    Submit(r.Bundle);

情境 B ── 長照(long-term care)要怎麼用?

長照是建在同一套 TW Core 地基上的另一本 IG。本 framework 的介面是中性的 (你給 PACase、我們依 CaseType 挑對應的組裝器),設計上「換一本 IG / profile 就能接」, 你的接法跟情境 A 一模一樣,只是 Ig/CaseType 不同。

誠實說:目前實作的是健保事前審查。長照組裝器在路線圖上,尚未實作 —— 這裡講的是「設計上如何接」,不是「今天已經能跑」。
