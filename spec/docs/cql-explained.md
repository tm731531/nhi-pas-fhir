# CQL 是什麼?一個 IT 工程師從零搞懂它的完整過程

> 這份文件不是規格書,是一段**真實的理解過程**。作者是 IT 出身,但第一次碰
> 健保的 CQL 規則時,腦中冒出的問題一個接一個 ——「它的資料庫是誰?」「規則要我寫成
> C# 嗎?」「它到底在哪裡執行?」。如果連 IT 都會卡在這些問題,沒碰過的人一定更卡。
> 所以我們把當時一問一答的順序**原封不動記下來**,每一題都用生活比喻回答。
> 跟著這 10 個問題走一遍,你就懂 CQL 在我們這個系統裡到底是什麼、擺在哪、怎麼用。
>
> 想看「怎麼接程式」的技術細節 → 看 [`cql-integration-notes.md`](cql-integration-notes.md)。
> 這份是「先把觀念想通」。

---

## 先給一句話結論

> **CQL 是健保官方寫好的「給付審查規則」。我們在把申請單送出去之前,先用『同一套規則』
> 在自己這邊跑一次,只送會過的、擋下會被核刪或缺資料的。等於考卷交出去前,先拿老師的
> 標準答案自己對一次。**

下面 10 個問題,就是把這句話一層一層拆開的過程。

---

## Q1.「CQL 跟我們的程式、跟 FHIR,到底是什麼關係?它的定位是什麼?」

我們原本的系統做兩件事:
1. **產** —— 把一筆事前審查申請組成一份 FHIR 文件(叫 Bundle,見 Q4)。
2. **送** —— 把這份文件 POST 給健保。

問題是:**送出去之後,健保會用一套規則審你,不合就核刪(事後把錢扣回去)。** 那套規則
健保其實**公開了**,格式就叫 CQL。

所以 CQL 的定位,是插在「產」和「送」中間的第三件事:
```
       產(組 Bundle) ──▶ 【CQL 自查】 ──▶ 送(POST 給健保)
                            ↑
                     用健保同一套規則,先在自己這邊審一次
```
它不取代「產」,也不取代「送」。它是**送之前的一道自我檢查**。

---

## Q2.「CQL 可以是一個 function,但它的對象是誰?它的資料庫是誰?」

這是最關鍵的一問。CQL 確實像一個函式 —— 但函式要有**輸入資料**才能算。那資料從哪來?

答案出乎意料:**資料就是我們自己剛剛產出的那份 Bundle。**

沒有另一個資料庫。CQL 不是去查健保的 DB,也不是查醫院的 DB。它審的對象,**就是我們
要送出去的那份申請文件本身**。

> 生活比喻:報稅軟體最後按「檢查」時,它不是去查國稅局的資料庫,而是檢查**你這張報稅單
> 填得對不對**。CQL 一樣 —— 它的「資料庫」就是你手上這張單子。

---

## Q3.「那這個資料庫,是我要自己建一個能吃 CQL 的嗎?」

不用。**你不需要蓋資料庫。** 承上題,資料就是那份 Bundle(一個 JSON 檔),不是一個要
架設、要維運的資料庫系統。

你**唯一要提供**的,是把那份 Bundle 準備得夠完整 —— 特別是**病史**(見 Q4 的坑)。

---

## Q4.「我們產的 Bundle 是什麼?」

**Bundle = 一份 FHIR 文件,把一筆申請需要的所有資料打包在一起的 JSON。** 裡面有:病人、
醫師、醫院、診斷(ICD 碼)、要申請的藥、檢驗報告……全部裝在同一包。

> 生活比喻:Bundle 就是「一整份申請卷宗」。不是零散的表格,是**釘在一起、一次交出去
> 的那一疊**。

⚠️ **這裡有個會咬人的坑:** 有些規則(續用藥、回診)會回頭查**病人以前的申請和用藥**。
如果你的 Bundle 只裝了「這一次」的資料、沒把病史一起打包進去,規則會查不到病史 ——
然後給出**跟健保不一樣的結論,而且不會報錯,是靜默的錯**。所以 Bundle 要當成一份
**縱貫的病歷**來組,不能只給當下這一筆。

---

## Q5.「所以這份 JSON,其實是我們整個 framework 最重要的 flow 吧?」

**對,完全正確。** 整個系統的主軸就是這份 Bundle 的一生:

```
產(組 Bundle)→ 驗(格式對不對)→ 查(CQL 自審)→ 送(POST)→ 回(收健保的核定)
```

Bundle 是這條流水線上**從頭到尾被傳遞、被加工的那個東西**。看懂 Bundle 的流動,就看懂
了整個框架。(這條 flow 的互動圖在 [`docs/flow.html`](../../docs/flow.html)。)

---

## Q6.「它檢查的規則是檢查什麼?這些規則是我要寫成 C# 的嗎?還是一個 binary 檔,我呼叫它就好?」

**規則不是你寫的,是健保寫好公開的。你也不用把它翻成 C#。**

- 規則檢查的是「這筆申請**符不符合給付條件**」—— 例如:年齡夠不夠、ICD 診斷碼對不對、
  該填的檢測(如荷爾蒙受體 HR)有沒有填、劑量在不在範圍。
- 這些規則你**不用重寫成 C#**。如果你手動翻成 C#,健保改規則你就要跟著改,而且很容易
  翻錯 → 反而製造核刪。
- 但它也**不是一個 binary 檔**。它是**文字檔**(人看得懂的 CQL),需要一個「執行環境」
  來跑(這就帶到 Q7)。

> 一句話:規則是健保的、文字寫的;你不重寫、只是拿來跑。

---

## Q7.「CQL 檔是文字檔,它必須要有一個執行環境。那個執行環境到底是什麼?」

對。文字檔不會自己算,要有東西去「執行」它。這個東西叫 **CQL 引擎**。

用大家熟的東西類比就秒懂:

| 你熟悉的世界 | CQL 的世界 | 角色 |
|---|---|---|
| SQL 原文(你寫的 query) | **CQL**(健保寫的規則,文字) | 人看得懂的規則 |
| 執行計畫(SQL 編譯後) | **ELM**(CQL 編譯後,見 Q8) | 機器要跑的形式 |
| **SQL Server**(真正去跑的引擎) | **CQL 引擎** | 執行環境 ← 這就是你問的那個 |

所以「執行環境」= **CQL 引擎**,地位等同 SQL Server。差別是:.NET 沒有成熟的原生 CQL
引擎,所以我們**接一個外掛的引擎程序(sidecar)**來當這個 SQL Server。

---

## Q8.「ELM?所以 CQL 其實是『下在』ELM 身上?」

**對,你抓到重點了。** 引擎真正跑的**不是**那份 CQL 文字,而是它**編譯後的版本 —— ELM**。

- **CQL** = 人寫、人看的規則(像 SQL 原文)。
- **ELM** = 把 CQL 編譯成機器好執行的形式(JSON/XML;**不是** binary,打開還是看得到結構,
  只是給機器讀的)。
- 每個規則檔健保都**同時附**了 CQL 文字版和 ELM 版。引擎吃 **ELM**,CQL 文字只是給人看的。

> 類比:CQL 是食譜(人讀),ELM 是這份食譜排好的標準化工序卡(機器照著做),引擎是廚師。

---

## Q9.「所以嚴格講,ELM(機器跑的)是規則。從我 C# 的角度,其實就是:POST 之前先丟給它做資料檢查,不要盲目送出去,一個『減壓』的動作?」

**完全正確,這就是它的本質。** 從我們程式的視角:

- 不做 CQL:組完 Bundle → **直接盲送** → 中了才知道被核刪(錢已經花了、卷宗已經送了)。
- 做 CQL:組完 Bundle → **先丟給引擎用官方 ELM 審一次** → 只送會過的,把會被核刪 / 缺件的
  擋在自己這邊。

這就是你說的「減壓」:**把健保端的核刪壓力,提前在自己這邊解決掉。** 它是**高信心的預測**,
不是保證 —— 最終核定權還是在健保(你會收到它的正式回覆)。但能先擋掉一大半明顯會死的。

⚠️ 補一個現實:自查最能**自動擋掉**的是「**該填的資料沒填**」(補件型)。而「條件不符」
(核刪型)裡有些還牽涉人工判讀、影像充足性,那些是 CQL 也編不出來的閘門 —— 所以輸出是
**三態**(通過 / 會被核刪 / 缺資料待補),不是單純的過 / 不過。

---

## Q10.「那『真引擎』到底在哪?」

不是遠方的神祕東西 —— PoC 已經在這台機器上跑起來過了,現在正式收進 repo:

- **位置**:[`cql-engine/`](../../cql-engine/)(放在 repo 根目錄,不綁 C#)。
- **語言中立的核心是 ELM 規則**(`cql-engine/elm/`)—— 任何合規的 CQL 引擎都能跑同一批。
  引擎**可換**:我們一開始試過一支 JS 參考 runner(`cql-engine/js/`,用 `cql-execution`),但它
  少了 `InCodeSystem`(規則要判斷「這個診斷碼屬不屬於某一版 ICD 系統」時要靠這個)這個能力,
  算不出忠實結果,所以**已改用 CQF-Ruler / HAPI clinical-reasoning(一台 server)當正式引擎**,
  JS runner 只留作歷史參考。**「引擎」不等於「那支 JS」,ELM 才是真正的資產。**
- **狀態**:已接上、跑得動真規則。C# 這邊 `ICqlEngine` 由 `CqfRulerCqlEngine` 實作,呼叫這台
  server 的 `Library/{ruleId}/$evaluate`,demo 會用到,整合測試是綠的。
- 細節與仍待補的小事(例如藥碼→規則對映表還不完整)→ 看 `cql-engine/README.md` 和
  `cql-integration-notes.md` §6。

## 更多常見問題(第一次接觸最容易冒出來的)

**Q11.「規則是誰寫的?會不會我要自己維護?」**
規則是**健保官方寫好、公開發布的**(CQL IG)。你不用自己寫、也不用翻成程式碼。你要維護的只有一件小事:
把官方發的新版規則**重新載進 server**。健保改規則 → 重載 → 拿同一份申請重跑,你的程式一行都不用改。

**Q12.「這樣會取代健保的審查嗎?」**
不會。這是**送出去之前、在自己這邊先自我對答案**,把明顯會被退的先擋下來。**最終核定權還是在健保**
(你會收到它的正式回覆)。它是「高信心預測」,幫你少送冤枉件,不是替健保決定。

**Q13.「我的病人資料會外洩嗎?」**
不會被送到外面。這台規則引擎是**你自己架的**(可以在自己機器、自己內網、自己網域下)。申請資料只在
「你的程式 → 你的引擎」之間走,不經過任何第三方。（這個 demo 用的全是**假資料**。）

**Q14.「為什麼要一台 server,不能純程式跑就好?」**
因為規則裡有些判斷(例如「這個診斷碼屬不屬於某一版 ICD 系統」)需要一個**完整、忠實**的 CQL 引擎才算得對。
我們試過純 JS 的輕量引擎,它**少了這個能力**會算錯;所以改用一台忠實引擎當「規則專用計算機」。你的主程式
只要把資料丟給它、收結果就好。

**Q15.「引擎以後想換掉呢?」**
換得很乾淨。引擎藏在一個介面(`ICqlEngine`)後面,你的申請資料(Bundle)、流程、畫面**都不綁**特定引擎。
今天用這台、明天換別台,只改中間那一小塊「插頭」。詳見 [`cql-wiring.md`](cql-wiring.md)。

**Q16.「自查說有一堆問題,那我實際送出去為什麼『沒事』?」**
這是最關鍵、也最容易被騙的一點:**健保「收件」不等於「核准」。**
你送出時,健保**當下會收下**(送出成功、看起來沒事)——但那些缺資料/不符條件的問題,**不是送出時爆,是
幾週後審查才爆 → 核刪(把已經給你的錢扣回去)。**
```
送出 → 健保收下(沒事!)→ …數週後審查… → 核刪(這時才「有事」,錢被追回)
```
所以「送出去沒事」是**假象、是陷阱**。自查的用途,就是把這個「事後才會爆」的核刪風險,**提前搬到送出前**,
讓你先補齊再送,而不是等被核刪才知道。這也是為什麼它叫「送**前**自查」。

## 一張表收尾:五個名詞,一次記住

| 名詞 | 白話 | SQL 類比 |
|---|---|---|
| **Bundle** | 我們要送出去的那份申請卷宗(JSON) | 要被檢查的那筆資料 |
| **CQL** | 健保寫好、公開的審查規則(文字) | SQL 原文 |
| **ELM** | CQL 編譯後、機器跑的版本(JSON,非 binary) | 執行計畫 |
| **CQL 引擎** | 真正去跑 ELM 的程式(我們接 CQF-Ruler / HAPI clinical-reasoning server) | SQL Server |
| **自查(這件事)** | 送出前用官方規則自己審一次,減壓 | 交卷前對標準答案 |

**把這五個擺對位置,CQL 就不神祕了。** 它就是:交卷前,拿老師公開的標準答案,自己先對一次。
