# 健保 ↔ FHIR:資料怎麼轉、系統怎麼接（遷移教學）

> 給「既有醫療/健保系統要開始接 FHIR」的人。不是規格書,是**把健保世界翻成 FHIR 世界的地圖**,
> 用我們實際做出來的「事前審查」當活教材。看完你會知道:健保資料長怎樣、FHIR 想要什麼、兩者怎麼對映、
> 怎麼漸進遷移、以及會踩哪些坑。

---

## 一、先認清:健保/醫療資料其實有「三個世界」

很多人以為「接健保 = 接 FHIR」,錯。台灣的醫療/健保資料交換**同時存在三套**,別搞混:

| 世界 | 是什麼 | 現況 | 標準長相 |
|---|---|---|---|
| **① 媒體申報(舊·主流)** | 健保**醫療費用申報**（門診/住院核銷） | **日常主力**,量最大 | 健保「醫療費用 XML 申報格式」:申報總表 / 點數清單 / 醫令清單 |
| **② FHIR IG(新)** | 健保/衛福部**新標準**,逐步導入 | 事前審查已上路;其餘陸續 | HL7 FHIR R4 + 台灣 IG(TW Core 地基) |
| **③ 長照(非 FHIR)** | 長照 2.0 評估/給付 | **沒 FHIR IG** | 照顧管理評估量表(CMS/ADL-巴氏/IADL)+ 長照四包錢給付基準 |

**關鍵認知**:
- **「沒有 FHIR IG」≠「沒有規範」** —— 媒體申報有正式格式規範、長照有量表規範。只是不是 FHIR。
- 一個真正的「健保工具箱」要能在**這三個世界之間轉**,不能只想 FHIR。
- 本專案目前做的是 **② 的事前審查(pas)**;媒體申報轉換、長照建模是路線圖上的獨立工單。

---

## 二、為什麼要往 FHIR 搬?

- **互通**:FHIR 是國際標準,病歷/申請能跨院所、跨系統交換(媒體申報是健保專用格式,出不了健保）。
- **已強制的入口**:**事前審查**已改走 FHIR 上傳。你不接 FHIR 就送不了某些事前審查。
- **結構化 + 可驗證**:FHIR 有官方 validator,能在送出前證明格式正確(媒體申報靠健保端退件才知道錯)。
- **可疊決策**:FHIR 之上能跑 **CQL**(健保公開的給付規則)做**送前核刪自查**——這是舊格式做不到的。

---

## 三、怎麼轉:健保欄位 → FHIR resource（概念對映）

FHIR 把一筆申請拆成「一份文件（Bundle）裝很多資源（Resource）」。健保欄位大致這樣落位:

| 健保世界的東西 | → FHIR Resource | 備註 |
|---|---|---|
| 病人（身分證/姓名/生日/性別） | `Patient` | 台灣用 TW Core `Patient` profile |
| 診斷（ICD-10-CM 碼） | `Condition` 或 `Claim.diagnosis` | ICD 碼要對到官方 CodeSystem（**坑見第六節**） |
| 就醫事件 | `Encounter` | |
| 醫師 / 醫院 | `Practitioner` / `Organization` | |
| 健保身分 | `Coverage` | |
| 要申請的藥/處置（醫令） | `MedicationRequest` / `Procedure` | 藥碼用健保藥品代碼 |
| 檢驗/影像/病理報告 | `Observation` / `DiagnosticReport` | |
| **「這是一筆申請」本身** | `Claim`（事前審查）或 `Task`+`QuestionnaireResponse`（重大傷病） | **不同 IG 用不同申請模型!** |
| 健保的核定回應 | `ClaimResponse` | 含核准/核刪/補件 |

⚠️ **最容易誤會的一點**:**不同健保 IG 的「申請」模型不一樣**。
- **事前審查(pas)**:申請 = `Claim`（一張保險理賠單的結構）。
- **重大傷病(ci)**:申請 = `Task` + `QuestionnaireResponse`（一張填好的申請表）。
所以「轉 FHIR」**不是一套對映走天下**,是**逐 IG / 逐案型找對映**(你說的「每個可能不一樣」就是這個)。

## 四、活教材:一筆事前審查,從健保描述 → FHIR Bundle

這是本專案已經做出來、可驗證的例子:

```
你給（健保世界的白話）:
  病人 + 診斷 ICD + 要申請的藥（藥碼）+ 檢測/影像 + 申報別/案件別
        │
        ▼  本工具(產)
一份 FHIR Bundle：Claim + Patient + Condition + MedicationRequest + Observation + …
  → 過官方 HL7 validator **0 errors**（對得上官方範例 Bundle-bun-1）
        │
        ▼  (查) 送前用健保官方 CQL 規則自查 → 通過 / 會被核刪 / 缺資料待補
        ▼  (送) 上傳（需醫事憑證 + 健保 VPN，見第六節）
        ▼  (回) 收 ClaimResponse（受理≠核准，核定事後才有）
```

程式對應:`NhiPas.Build(case)` 產 Bundle、`Pipeline.RunAsync(case, cql:)` 跑產→驗→查。你只給一個中性的
`PACase`（完全不碰 FHIR),工具把它翻成 FHIR。**這就是「既有系統怎麼接」的答案:你的系統給資料,工具講 FHIR。**

## 五、另一個方向:媒體申報 XML ↔ FHIR（研究中）

日常健保核銷走的是**媒體申報**(不是 FHIR)。要做完整工具箱,得能雙向轉:
- **媒體申報 → FHIR**:把申報總表/點數清單/醫令清單的欄位,對映成 FHIR 的 Claim/Encounter/資源。
- **FHIR → 媒體申報**:反過來,讓 FHIR 產出的資料能落回健保申報。
- **規範來源**:健保署「醫療費用 XML 申報格式」有公開規格 + 歷次修改版(nhi.gov.tw）。
- **現況**:這是本專案的獨立工單（逐案型:門診/住院/事前審查各有格式),**尚未實作**,誠實標明。

## 六、既有系統（HIS/EMR）怎麼漸進遷移

不用一次全換。務實路徑:
1. **先接被強制的**:事前審查已走 FHIR → 先做這個入口。
2. **保留舊管道**:一般費用申報繼續走媒體申報,別為了「全 FHIR」硬改還沒強制的。
3. **中間放一層轉換器**:你的 HIS 已經有病人/診斷/醫令的資料 → 對映成中性 case → 由工具產 FHIR。你的 HIS **不用學 FHIR**。
4. **送出前先自查**:接上 CQL 送前自查,擋掉會被核刪的,再送 → 少被扣錢。

## 七、真實會咬人的坑（我們踩過的）

- **TW Core 0.3.2 的 ICD CodeSystem url 有 bug** → closed slicing 連鎖崩,連官方範例都噴 25 錯。要補 terminology patch 才驗得過。
- **CQL Bundle 必須是「縱貫病歷」** → 續用/回診規則會回頭查病史,漏放病史會**靜默判錯**。
- **收件 ≠ 核准** → 健保收件當下看似沒事,核刪是**事後**才發生。這是最危險的假象,也是送前自查的理由。
- **「真的送出」要三把鑰匙** → 健保正式 endpoint + **醫事憑證(HCA)** + **健保 VPN/專線**。這三樣要**醫事機構身分**才拿得到(你的診所、或有授權的合作醫院如合作醫院）。**沒憑證,任何人都送不進健保** —— 這是資格題,不是技術題。
- **正確性只認官方 validator** → 別「看起來對」就送;每份輸出過官方 validator 0 errors 才算數。

## 八、各 IG / 領域的遷移狀態（誠實版）

| 領域 | 世界 | 狀態 |
|---|---|---|
| 事前審查 (pas) | FHIR | ✅ 已做（本 repo 的活教材） |
| 重大傷病 / 電子處方箋 / NGS / EMR / 傳染病 / 健保基礎 | FHIR | ⬜ 已發布可做,路線圖上,一本一本建 |
| 媒體申報（費用申報） | 舊 XML | ⬜ 有規格,研究中,尚未實作 |
| 長照 | 非 FHIR（量表/給付） | ⬜ **無 FHIR IG**;走量表/給付規範建模,尚未實作 |

**原則貫穿全篇:做多少、說多少;沒做好的,絕不宣稱做好了。**
